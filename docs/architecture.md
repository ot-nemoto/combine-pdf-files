# アプリケーション設計書

## 概要

**combine-pdf-files** は、ブラウザ上で完結する PDF 結合ツール。
複数の PDF を読み込み、ページ単位で並び替え・回転・削除を行ってから 1 つの PDF として出力する。
サーバーサイド処理は一切なく、PDF 操作はすべてクライアント側の `pdf-lib` で実行される。

> ディレクトリ構成・型定義・関数シグネチャ・コンポーネント内部実装はコードを source of truth とし、本書には記載しない。本書は「なぜその構成なのか」という設計意図・契約・規約を扱う。

## 環境変数

| 変数 | 用途 |
|------|------|
| `BUILD_MODE` | `static` を指定すると GitHub Pages 向け静的エクスポート（`output: "export"`）を有効化する。設定内容は `next.config.ts` を参照 |

## ビルド・デプロイの契約

- **通常ビルド**（開発・SSR）と **静的エクスポート**（GitHub Pages 向け）の 2 系統を持つ。
- 静的エクスポートは `BUILD_MODE=static` のときのみ有効化され、`basePath` / `assetPrefix` に `/combine-pdf-files` を付与する。GitHub Pages のサブパス配信に合わせるための契約であり、**具体値は `next.config.ts` を source of truth とする**。
- デプロイは `.github/workflows/deploy-github-pages.yml` が `develop` への push を契機に自動実行する。手動デプロイは不要。トリガー・手順の詳細はワークフローを source of truth とする。

## 設計上の判断（意図）

コードから読み取れない「なぜ」を記録する。実装の詳細はコードを参照。

1. **サーバーレス設計** — PDF 処理をすべてクライアントで完結させ、ファイルをサーバーに送信しない。プライバシー確保が目的。この制約が「静的エクスポートで配信可能」という要件を規定する。

2. **ページ単位のバイナリ管理** — 各ページを独立した 1 ページ分の PDF バイナリとして保持する。任意順の結合・削除・回転を、元ファイルの構造に依存せず単純に扱えるようにするため。

3. **状態管理の集約** — アプリ全体の状態を単一のカスタムフックに集約し、画面コンポーネントはその返り値を受け取るだけにする。状態遷移のテスト（`renderHook`）を容易にする意図。

4. **競合防止（リクエスト ID）** — 複数ファイルを素早く選び直した際に、古い非同期処理の結果が最新の状態を上書きしないよう、リクエスト ID で結果の採否を判定する。

5. **Blob URL のライフサイクル管理** — プレビュー用に生成する Blob URL は、不要になった時点で解放する。長時間操作でのメモリリークを防ぐための契約。プレビュー URL の再生成は必要最小限の依存でのみ発火させる。

6. **ドラッグネスト問題の回避** — ドラッグ&ドロップ判定は、子要素への移動で `dragleave` が誤発火する問題をカウンタ方式で吸収する。ドロップ時は MIME タイプ `application/pdf` でフィルタし、PDF 以外は無視する。

## バージョン固有の gotcha

フレームワーク・ライブラリのバージョン更新時に踏みやすい注意点を記録する（発生都度追記）。

- Tailwind CSS v4 系ではユーティリティ設定を CSS 側（`@theme`）で行う。設定ファイルベースの旧来手法とは異なる。
- 現時点で個別の既知 gotcha はなし。
